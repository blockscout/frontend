The CI workflows and release tooling in this repo are owned by the frontend team (tom); DevOps owns only the
demo-deploy and cleanup workflows and is not a contact for this task.

## Context & goal

Patch releases are built from hand-made cherry-picks on a `release/vX.Y.Z` branch, so the previous tag is
never an ancestor of `main`. Release notes are generated from a SHA range, so every backported PR reappears
in the next minor's notes and is removed by hand (8 PRs in the last minor). Nothing links a backport to its
source PR, PRs are never labeled with the version that shipped them, the PR template is not enforced, and
category labels are optional — so notes generation and backporting rely on reading and tribal knowledge.

The target is a workflow where "what shipped where" is a label query, every release-branch commit names its
source commit and PR, and each phase (prepare, alpha, publish) is one command with a reviewable
artifact, for a minor and a hotfix alike. The first release cut on the new scheme is v2.13.0; the v2.12
line already on staging finishes on the current process.

Verified during grilling against the v2.11 patch line: of the four PRs that were hand-backported there,
three cherry-pick from their `main` squash commit with zero conflicts and the fourth (#3708) yields two
modify/delete conflicts because a refactoring on `main` touched files the release branch lacks — resolved by
dropping those files. Conflicts are resolved once: the release branch is never merged back to `main`.

## Functional requirements

1. `main` is trunk. Every release `vX.Y.Z` has its own branch `release/vX.Y.Z`, cut by the prepare command:
   from `main` for a minor (`Z = 0`), from the line's previous final tag `vX.Y.(Z-1)` for a patch. Every tag
   of the release, alpha and final, is on that branch. Nothing is committed only to a release branch except
   the docs commits from prepare and alpha, which return to `main` by `git cherry-pick -x` at publish.
2. Every non-docs commit on a release branch is a `git cherry-pick -x` of a `main` squash commit: its
   message carries `(cherry picked from commit …)` and the original `(#N)`.
3. The final-release workflow labels every PR shipped by the tag with the `vX.Y.Z` label, in addition to the
   linked issues it labels today. The pre-release workflow applies `pre-release` to PRs the same way and the
   final-release workflow removes it from PRs as it does from issues today.
4. Commit → PR resolution: the `cherry picked from commit <sha>` trailer first, then `(#N)` in the subject,
   then GitHub's commit → PR association. A PR that already carries any `v*` label is never relabeled and
   never listed again.
5. Release notes for `vX.Y.0` = PRs merged to `main` since the fork point of the previous minor
   (`merge-base(main, previous minor tag)`) that carry no version label. Notes for `vX.Y.Z` = the PRs picked
   onto the branch since the previous tag. Both use the same section generator; empty sections are omitted.
   The generated list for a minor needs no manual removal of previously released PRs.
6. `backport` on a merged PR means "ship in the release being prepared". Prepare and alpha pick every such
   PR not yet on the release branch, in `main` order, before generating the notes. A PR is on the branch
   when its `main` commit is an ancestor of the branch head or a branch commit's trailer names it. Picking
   stops on a conflict and is idempotent, so re-running the command resumes it; the commands print the PRs
   they skipped. `backport` is replaced by the version label when the PR is released; a PR that was not
   picked keeps `backport`.
7. A `pull_request` check fails when the body lacks a heading of `docs/PULL_REQUEST_TEMPLATE.md`, still
   contains the template's placeholder text, carries no category label, carries labels of more than one
   category (release-notes section), or combines `dependencies` with any other category. Several labels of
   one category pass. PRs labeled `release` are exempt.
8. `chore` is the catch-all category ("Other changes"). The section ↔ label mapping has one source of truth
   in the release tool; `docs/RELEASING.md` reproduces it and a unit test fails when the two drift.
9. One GitHub pre-release per release, minor or patch: created as a draft by prepare (its only creator),
   re-pointed to each new alpha tag with its notes regenerated by the alpha command, turned into the final
   release by publish. Alpha fails when the release has no pre-release; a line never has two open
   pre-releases.
10. Prepare and alpha replace every `upcoming` on the release branch, including what a picked PR brings,
    with `vX.Y.Z+` in a docs commit. A tag whose ENV docs still contain `upcoming`, or whose notes list a
    PR already carrying a version label, fails both in the CLI before pushing and in CI (`pre-release.yml`
    and `release.yml`) before the image is built.
11. `docs/RELEASING.md` holds the decision table ("I need to… → run …") and one state diagram; the skills
    reference it rather than restating it. `create-pr` reads `docs/PULL_REQUEST_TEMPLATE.md` instead of
    carrying a copy.
12. The staging roll-up Slack request keeps today's content: breaking ENV changes derived from the PR
    bodies' "Environment variables" sections.
13. Project-card updates ("Released" status) keep working from the labeled issues as today.

None. No endpoint, env var, feature flag, or analytics event. GitHub API via `GITHUB_TOKEN` in CI and the
operator's `gh` auth locally.

## UI inventory

None. Developer tooling, CI workflows, docs, and agent skills only.

## Implementation decisions

### One module backs CI and the skills

- `tools/release/` is a TypeScript module in the repo's `tools/<name>/` shape (co-located `*.spec.ts`,
  `run.sh`, under `pnpm lint:tsc`, the complexity gate and Vitest). It exposes one CLI with subcommands:
  `prepare`, `alpha`, `publish`, `label`, `notes`, `check-pr`, `check-tag`. Picking is a step inside
  `prepare` and `alpha`, not a subcommand.
- Pure logic is separated from GitHub/git I/O and unit-tested: trailer and `(#N)` parsing, label-set
  computation, exclusion of already-versioned PRs, notes query construction, section mapping, PR-body
  validation, the `dependencies`-stands-alone rule, drift check between the mapping and `RELEASING.md`.
- Workflow steps shrink to checkout + install + one CLI call. The inline `actions/github-script` logic in
  `label-issues-in-release.yml`, `release.yml` and `pre-release.yml` moves into the module; the
  `fetch-release-prs.js` script in the `prepare-release` skill is removed.
- Labeling stays workflow-driven (release events), not CLI-driven, so the guarantee is independent of who
  ran the command; the CLI waits for the run and reports.

### Phases

A minor and a hotfix run the same three phases; they differ only in where prepare cuts the branch.

- `prepare vX.Y.Z`: cut `release/vX.Y.Z` (from `main` for `Z = 0`; for a patch, from `vX.Y.(Z-1)`, which
  must be the line's latest final tag); pick; release `upcoming` in `docs/ENVS.md` and
  `docs/DEPRECATED_ENVS.md` as `vX.Y.Z+` in a docs commit; generate notes from the labeled set; create the
  draft pre-release. No changelog file is committed — the draft release is the reviewed artifact.
- `alpha vX.Y.Z-alpha.N`: on the branch inferred from the version, pick and release `upcoming` again, then
  re-point the pre-release to the tag with regenerated notes, tag, push (fires `pre-release.yml`, one image
  per tag), then the existing staging-request flow.
- `publish vX.Y.Z`: tag the approved alpha commit again as `vX.Y.Z`, publish as the final release marked
  latest (fires `release.yml`), cherry-pick the release's docs commits to `main` with `-x`.
- Picking (inside prepare and alpha): query merged PRs with `backport` and no version label, cherry-pick
  `-x` in `main` order the ones not on the branch, stop on conflict, run checks before pushing.
- Fixes found while a release is on staging take the hotfix path into it: PR to `main`, `backport` label,
  the next `alpha` picks it.

### Operator model

- The skills run in a session with the developer present. Prepare and alpha work on the operator's
  checkout of the release branch. On a pick conflict the agent may resolve it but never runs `--continue`
  or pushes until the developer has approved the resolved diff; after `--continue` the same command is
  re-run.

### Labels

- Reuse `chore` as the catch-all; create `backport` and `release`. Allowed category set = every label in the
  mapping table (`feature`, `enhancement`, `client feature`, `bug`, `performance`, `dependencies`, `design`,
  `refactoring`, `tech`, `devops`, `chore`). `dependencies` is only for PRs whose sole purpose is bumping a
  package version.
- The `pre-release` and version label jobs must not derive the PR set from a bare SHA range: with the
  release branch, the previous release can sit on another branch, so the range would include already
  shipped PRs. The exclusion in requirement 4 is what keeps them correct.

### Docs and skills

- `docs/RELEASING.md` is linked from `docs/CONTRIBUTING.md`; `RELEASE_NOTES.md` moves into `tools/release/`
  as the generator's template.
- `prepare-release` is replaced by one `release` skill around the CLI that covers a minor and a hotfix.

### Delivery

- One PR for the whole task, in the usual medium/big-task shape.

## Out of scope

- Computing staging ENV deltas against the live instance config.
- A per-PR backport GitHub Action.
- Renaming or rewriting history of existing release branches; the v2.12 line.
- Preparing two releases at once: a `backport` PR goes to whichever release picks it first.
- Changing the project-management, deploy, cleanup, or e2e workflows beyond the label calls above.
