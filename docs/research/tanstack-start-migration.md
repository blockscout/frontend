# Migrating from Next.js (Pages Router) to TanStack Start

Research notes, 2026-11-02. Repo state: `main` @ `42f58c665`, Next.js 16.4.3, React 19.1.4, Vite 8.3.5 (already a devDependency for Vitest / Playwright CT), TanStack Query 5.55.4, no TanStack Router. Counts below were taken with `grep`/`find` over `src/`, `deploy/`, `tools/`, `playwright/`, `vitest/` (excluding `node_modules`, `.next`, `.claude/worktrees`). TanStack facts are from the official docs / GitHub as of this date; where a doc page did not state something, the row says so rather than guessing.

## TL;DR / Recommendation

**Defer. Do not open the migration PR now.** Three findings drive this:

1. **Start 1.0 went stable three weeks ago** ([blog, 2026-10-13](https://tanstack.com/blog/tanstack-start-1-0): "TanStack Start 1.0 is finally stable"; current `@tanstack/react-start` is 1.169.4). The APIs are committed, but the RC→1.0 guide still lists removed APIs and changed error semantics ([migrate-from-release-candidate](https://tanstack.com/start/latest/docs/framework/react/migrate-from-release-candidate)), the official "Migrate from Next.js" guide covers the **App Router only** ([link](https://tanstack.com/start/latest/docs/framework/react/migrate-from-next-js)), and several surfaces this repo depends on (CSP nonce plumbing, request-body limits, React Compiler, runtime-added static files) are documented only in PRs or third-party guides.
2. **The coupling is wide, not deep: 273 source files import `next/*`, 130 more import `nextjs-routes`, 89 files export `getServerSideProps`, 63 Playwright tests stub `next/router`, and the Docker image, entrypoint, dev-server tooling, ESLint, tsconfig, Rollbar filters and the agent skills all assume Next.** Estimate for a single PR: **~90–125 agent-hours plus ~35–45 human review hours**, with at least four decisions that only a human can take (§5).
3. **The runtime-env contract collides with Vite's static-asset model.** The container writes `envs.js`, favicons, the OG image, sitemap, multichain config and downloaded JSON configs into `public/` *at startup* (`deploy/scripts/CONTEXT.md`); Vite copies `public/` into the build output *at build time* ([Vite assets guide](https://vite.dev/guide/assets)). How Nitro's node server serves files that appear after the build must be proven before anything else is written — it is the one item that could sink the plan.

What *is* worth doing now, framework-agnostically, is the prep in Phase 2 (a router facade and a `route()` shim); it shrinks the eventual diff from ~400 files to ~50 and pays off even if the migration never happens.

Automated, agent-runnable:

- `pnpm lint:tsc`, `pnpm lint:eslint`, `pnpm lint:cspell`, `pnpm lint:doc-links`, `pnpm presets:lint` — must be clean; tsc is the primary regression net for the 400-file codemod.

- `pnpm test:pw` full run (229 files, 3 projects) — force-full because `playwright-ct.config.ts` changes; screenshot diffs should be zero for everything that is not a route shell.
- `pnpm dev:preset eth` smoke + `pnpm prod:preset eth`: curl every one of the 84 routes with a representative param (there is no e2e suite in this repo; `e2e-tests.yml` runs against a k8s deploy), assert 200/404 parity against `eth.blockscout.com`, assert the CSP header, `Set-Cookie` for uuid/colour-theme, and the redirect table (75 URLs, status code + `Location`).

## 4. Pitfalls requiring a decision before starting

1. **Runtime-written static files vs build-time `public/`.** Everything the entrypoint generates lands in `public/` after the build (§1.4). Vite copies `public/` at build time ([Vite](https://vite.dev/guide/assets)); whether Nitro's node preset serves a file that appears in `.output/public` later is not documented on the pages read here. Options: (a) prove Nitro serves from disk and write there; (b) serve `/assets/*`, `/sitemap.xml`, `/robots.txt`, favicons from a splat server route reading the filesystem; (c) move `envs.js` to a server route that renders `window.__envs` from `process.env` on request (keeps the URL, drops the file). (c) also keeps the primer and `getEnvValue` untouched. **Must be decided first; it shapes Phases 2, 4 and 7.**
2. **URL compatibility — search params.** Blockscout URLs are linked from everywhere and the app round-trips `?tab=`, `?page=`, `?items_count=`, `?block_number=`, hex hashes and JSON-ish filters through `router.query` (208 reads) and `useQueryParams`. TanStack's default parser turns `page=2` into a number and `desc=true` into a boolean, and writes nested values as JSON ([search-params](https://tanstack.com/router/latest/docs/framework/react/guide/search-params)). Decision: supply `parseSearch`/`stringifySearch` that keep strings strings and arrays as repeated keys, exactly as `URLSearchParams` does today, and set `trailingSlash: 'preserve'` (the redirect table contains `/tokens/?tab=bridged`). Without this, every shared link and the primer's byte-for-byte URL match (`src/server/primedRequests/CONTEXT.md`) break.
3. **Keep `NEXT_PUBLIC_*` and `window.__envs`, or move to `VITE_*`?** Start's model inlines client envs at build time ([env docs](https://tanstack.com/start/latest/docs/framework/react/guide/environment-variables)); this repo's whole model is one image, runtime envs, validated by `envs-validator` and documented in `docs/ENVS.md` (200+ variables, external operators). Recommendation: keep the names and the `window.__envs` contract unchanged in this PR; a rename is a separate, operator-facing deprecation cycle (`deprecate-env-var` skill).
4. **Primer and CSP nonce.** The primer is allow-listed by startup-computed hashes and must stay request-independent. Start's own hydration scripts are nonce'd via `router.options.ssr.nonce` ([PR #5522](https://github.com/TanStack/router/pull/5522)); today the nonce exists only when Sevio ads are on. Decision: keep hash-based primer + optional nonce (as now), or go nonce-always (simpler CSP, but `src/server/csp/index.ts` caches policies and would template every request). Also decide whether loaders + `ssr-query` streaming *replace* the primer for home/tx/address — that changes the loading-perf baseline the ADR 0003 numbers rest on.
5. **Nitro or a hand-written Node server.** Nitro is the documented Node path and gives `.output/server/index.mjs`, `PORT`/`HOST`, graceful shutdown ([Nitro](https://nitro.build/deploy/runtimes/node)). The repo also needs pino-http logging, prom-client `/metrics`, OTel auto-instrumentation of the HTTP server, the 100 MB proxy body, and `Server-Timing`. Those are all doable as server routes / middleware, but OTel's `instrumentation-http` hooks assume Node's `http` server, which Nitro's node preset does use. Decide Nitro (default) vs Rsbuild+`srvx` (not Vite — rules out reusing the CT config).
6. **The toolkit's `Link`.** `src/toolkit/chakra/link.tsx` imports `next/link` and is published as `@blockscout/ui-toolkit`. Making it router-agnostic (inject the anchor component, or `asChild`) is an API change for external consumers and should ship (Phase 1) before any Start code.
7. **`/node-api/*` and the config endpoint.** The dev-server registry, the demo deploy, the `resolve-api-url` skill and external tooling fetch `/node-api/config`. Mount server routes at `/node-api/...` directly rather than re-creating the rewrite; keep the JSON shape.
8. **Redirects (75) and 404/500 pages.** Next's redirect table runs before any route (including `has: query` matchers and `permanent`). In Start the equivalent is a request middleware or `beforeLoad` redirects; `redirect()`'s HTTP status handling is on the `Redirect` type page, not covered by the guides fetched — verify 301 vs 302 parity in Phase 0. `_error.tsx` reports to Rollbar server-side; map to `defaultErrorComponent` + a request-middleware catch.
9. **ESLint and the eslint-alternatives research.** `@next/eslint-plugin-next` goes; `docs/research/eslint-alternatives*.md` assumed it in the oxlint migration plan — the swap simplifies that plan (one plugin fewer to JS-plugin). Add `@tanstack/eslint-plugin-router` (`create-route-property-order`).
10. **Playwright CT.** Already Vite 8 + Rolldown with the aliases a Start build will need — reuse them in `vite.config.ts`. The `next/router` alias and `hooksConfig.router` in 63 tests become a `RouterProvider` with `createMemoryHistory` ([setup-testing](https://tanstack.com/router/latest/docs/framework/react/how-to/setup-testing)); `define: { 'process.env': '__envs' }` stays.
11. **TypeScript 7 side-by-side (ADR 0004).** Start's Vite plugin generates `routeTree.gen.ts` and does not need the TS compiler API; `typescript-eslint` still pins TS 6. No change needed, but Next's `typescript.ignoreBuildErrors` reasoning in the ADR becomes moot — update the ADR.
12. **Profiling / bundle analysis.** `tools/profiling` relies on `next build --webpack --profile`; in Vite it is a `resolve.alias` of `react-dom` → `react-dom/profiling` behind a flag; `@next/bundle-analyzer` → a Rolldown visualizer. ADR 0003's two "stays on webpack" rows disappear — write ADR 0005 superseding it.
13. **Rollbar own-bundle filter.** `/_next/` is hard-coded in `src/services/rollbar/queue.ts` and `utils.ts`; the Vite asset prefix (default `/assets/` — which collides with this repo's `public/assets/` convention) must be chosen (`build.assetsDir`) and the filter plus its specs updated.
14. **Body size for the proxy route.** `pages/api/proxy.ts` sets a 100 MB limit (contract verification uploads). Start's server-routes docs say nothing about limits; Nitro/h3 defaults must be measured in Phase 0.
15. **Concurrent page work.** Any PR touching `src/pages/**` during the migration window will conflict with Phase 3 — freeze or rebase policy needed.
16. **Scope of SSR.** Today nothing below the shell is server-rendered (`PageNextJs` + `useIsMounted`). Keeping `defaultSsr: false`/`'data-only'` preserves behaviour and the visual baseline; turning SSR on is a separate performance project with its own CSP/hydration risks and should not ride on this PR.

## 5. Recommendation

**Defer the framework switch; land the decoupling now.**

- *No-go for a single PR this quarter*: 1.0 is three weeks old, the Next.js migration guide targets the App Router, two of the contracts this repo lives on (runtime-written `public/`, hash-allow-listed primer + optional nonce) are only provable by spike, and the diff is ~400 source files plus Docker/entrypoint/dev-server/tests/tooling/agent docs — too much for one review even in phases. The upside is unquantified: ADR 0003 already got the build to 87 s and halved FCP on Turbopack, and the repo does not use App Router, RSC, `next/image` or `next/font`, so the Pages Router is not holding anything back today.
- *Do now*: Phase 1 (router facade, `route()` shim, toolkit `Link` injection). It is framework-neutral, shrinks the future migration to ~50 touched files outside `src/pages`/`src/server`, and unblocks the oxlint plan regardless.
- *Re-evaluate* when: Start has ≥2 months of 1.x patch history, the hosting docs cover runtime static files — or when Next.js forces a move (Pages Router deprecation).

Top 5 decisions a human must make first:

1. **How runtime-generated files (`envs.js`, configs, favicons, OG, sitemap) are served** under Vite/Nitro — disk-served `.output/public`, splat server route, or `envs.js` as a server route (§4.1).
2. **URL contract**: custom string-preserving `parseSearch`/`stringifySearch`, `trailingSlash: 'preserve'`, and where the 75 redirects live (middleware vs `beforeLoad`) — every current URL must keep working (§4.2, §4.8).
3. **Server runtime**: Nitro node preset (documented path) vs anything else, given OTel, pino, prom-client, the 100 MB proxy body and `Server-Timing` (§4.5, §4.14).
4. **Env model**: keep `NEXT_PUBLIC_*` + `window.__envs` + `/node-api/config` byte-compatible in this PR (recommended) vs start a `VITE_`/rename deprecation cycle (§4.3).
5. **SSR scope and the primer**: keep `ssr: false`/`'data-only'` everywhere and the hash-allow-listed primer (behaviour-preserving) vs adopt loaders + `ssr-query` streaming and a nonce-always CSP (a performance project with its own ADR) (§4.4, §4.16) — plus the toolkit `Link` API change that must ship first (§4.6).
